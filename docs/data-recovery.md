# 采集历史与个人备份恢复

## 云端采集历史

采集 SQLite 存入本仓库的 GitHub Release 附件，每次运行创建独立的 `radar-data-<run_id>-<attempt>` 快照。`state/snapshot.json` 只保存已完成上传、重新下载并通过恢复验证的快照指针。Git 不再随每次采集追加整份数据库。

每份快照含 `history.db.gz` 和 `manifest.json`。恢复同时验证压缩包摘要、SQLite 完整性、文章 ID 唯一性、文章数量、首次收录日期范围、各来源检查点与摘要缓存条数；测试还覆盖实际文章和缓存内容的往返保留。校验失败不会用空数据库继续采集，也不会替换已有目标文件。

保留最近 14 份自动快照；指针引用的版本和一次性迁移种子长期保留。清理仅针对本工具命名的自动数据快照，不删除软件版本。Git 里过去已经存在的二进制历史不重写，避免影响其他克隆；迁移后不再增长这类提交。

新环境安装 GitHub CLI、登录有仓库读取权限的账户并安装 `radar/dev-requirements.txt` 后：

```sh
python radar/snapshots.py restore --database recovery-check/history.db
python radar/run.py build --data-dir recovery-check --output recovery-site
```

目标数据库必须尚不存在。先在独立目录恢复并检查文章、日期、摘要和来源状态，再停止本机组件，将确认好的数据库接入应用。不要覆盖运行中的 SQLite 数据库；本机的 `archives.db` 和 `library.json` 与云端采集历史是不同文件。

恢复某个保留版本时，将 Releases 页上的实际标签传给 `--tag`：

```sh
python radar/snapshots.py restore --tag <实际快照标签> --database recovery-older/history.db
```

GitHub 附件下载失败时保留当前服务和已发布页面，修复网络或权限后重试；不要删掉快照指针来绕过失败。首次迁移前的版本才允许从旧 `state/history.db.gz` 引导。

GitHub Release 附件机制参考：[GitHub 官方说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

## 网页与本机阅读内容

侧边栏「导出完整备份」生成 v4 JSON：已读、收藏、自选期刊、收藏文件夹、相应文章与手动引用修正、完整缓存译文、个人期刊组、新增期刊配置和自动翻译开关。翻译邮箱、访问令牌和额度记录不进入备份。

在另一台设备或另一版本点击「导入备份」，选择该文件即可合并。目标已有收藏和期刊配置不会被整份替换。期刊按 ID、ISSN 或 RSS 来源匹配；同一分组保留目标名称、合并成员。源设备删除的内置可编辑组只在目标仍未修改该组时移除。

网页版接收新增期刊的配置与已保存文章，显示为备份期刊；新文章采集仍由本机版执行。导入本机版后可点击「本机补采」。不需要先手动创建同名期刊。无效的旧备用 ISSN 不写入新备份，规范的期刊 ID 和有效别名仍保留。

v1–v3 备份继续兼容；它们没有个人期刊配置。旧备份若引用未安装的期刊，应在原设备升级并重新导出完整备份，或先添加对应期刊。导入失败会提示失败原因，已完成的合并保留；修正后可重复导入，不会重复生成同一篇文章。

本机「迁移网页版内容」使用同一 v4 格式，携带文章、译文和配置，不再只传收藏 ID。网页与本机依然是两个独立存储来源；每次迁移是一次合并，不是持续自动同步。

## 网页数据与离线边界

`index.json` 包含期刊信息和最新收录的 600 篇文章；更早记录按期刊分片，每片最多 250 篇，使用内容地址。搜索、查看单刊、切换全部时间或点击「加载更早文章」时才获取相关历史。收藏已有的文章副本独立保存，不依赖再次加载历史。

`data.json` 暂保留为旧客户端的完整兼容入口，新版首页不请求它。采集端补摘要后重新生成清单和分片；产物校验要求分片重组结果逐条等于完整集合。

离线可阅读已缓存页面、近期文章、已访问的历史分片和收藏。最多缓存 80 份历史分片；未访问或被淘汰的更早文章需要联网。APA 处理器首次使用时下载，之后可离线处理已有引用信息；缺失的 Crossref 元数据仍需要联网补取。
